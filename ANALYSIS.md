# Анализ кодовой базы PPR-Client

Дата анализа: 2026-01-25

---

## 1. Оценка архитектуры

### Сильные стороны
- **FSD (Feature-Sliced Design)** с нумерованными слоями — чёткое разделение ответственности
- **Server Actions** — современный подход Next.js 14 для мутаций
- **Явные кросс-импорты** через `@x/` — хорошая практика контроля зависимостей
- **Drizzle ORM** — типобезопасная работа с БД
- **React Context** для состояния — подходит для масштаба проекта

### Проблемы архитектуры

| Проблема | Файл | Влияние |
|----------|------|---------|
| **Монолитный PprProvider** | `src/2entities/ppr/ui/PprProvider.tsx` | 881 строка, 40+ методов. Нарушает SRP |
| **Бизнес-логика в entities** | `PprProvider.tsx` | Должна быть в features слое |
| **Расчёты в TSX** | `correctionRaport/`, `reports/` | Сложная логика в UI-компонентах |
| **Дублирование кода** | `calculateLaborCost.ts`, `calculateFulfillmentReport.ts` | 26 строк копипасты в каждом файле |

## 2. Оценка тестового покрытия

### Статистика
| Метрика | Значение |
|---------|----------|
| Файлов с тестами | 4 unit + 3 e2e |
| Всего файлов | 193 |

### Что покрыто
- Утилиты `math`, `date` — хорошие параметризованные тесты
- `authConfig` — с моками
- `createPprMeta` — с фикстурами

### Что НЕ покрыто (критично)
- **Server Actions** (`ppr.actions.ts` — 707 строк)

- **XLSX экспорт** (сложная бизнес-логика)
- **Расчёты отчётов** (`calculateFulfillmentReport`, `calculateLaborCost`)

### Вердикт
**Критически низкое покрытие.** При рефакторинге высок риск регрессий.
